# المرحلة الرابعة — نقل الخدمات الثقيلة

هذا المستند يصف **ما بُني فعلًا** في المرحلة الرابعة، وما لم يُبنَ،
وكيف يُشغَّل النقل خطوة خطوة.

---

## ١. الفكرة في سطر واحد

كل نداء ذكاء اصطناعي في المنصة — **٣١ موضعًا في ٣٠ ملفًا** — بيمرّ من
دالة واحدة: `AIService.execute`. المحوّل اتحطّ **جوّه الدالة دي**، فملف
واحد اتغيّر، والـ٣١ موضع اتنقلوا مع بعض، وصفر تعديل على أي مستدعي.

```
مستدعٍ (٣١ موضعًا، بلا تعديل)
   ↓
AIService.execute            ← المحوّل هنا
   ├── العلم مطفأ؟ ──────────→ AIService.executeDirect (المسار القديم)
   ├── مفيش عامل حيّ؟ ───────→ AIService.executeDirect
   ├── الطلب فيه وسائط؟ ─────→ AIService.executeDirect
   └── غير كده ──────────────→ الطابور → عامل الخدمة → بوابة الذكاء
                                      ↓ (فشل / مهلة)
                                AIService.executeDirect
```

**الخاصية الحاكمة:** كل سهم خطأ بيرجع للمسار القديم. أسوأ حالة في
المسار الجديد بطء، مش توقّف.

## ٣. طبقات الأمان الخمس

مرتّبة من الأسرع للأبطأ في الاستجابة:

1. **`MIGRATION_KILL_SWITCH=on`** — متغيّر بيئة واحد، بلا قاعدة بيانات
   ولا نشر. يرجّع المنصة كلها للقديم في دقيقة. هذا هو إجراء الطوارئ.
2. **`MIGRATE_<SERVICE>=off`** — تجاوز بيئة لخدمة واحدة. يغلب قاعدة
   البيانات، لأن القاعدة نفسها قد تكون مصدر العطل.
3. **إطفاء العلم من اللوحة** — ينتشر خلال ١٠ ثوانٍ (مدّة الذاكرة).
4. **فحص العامل الحيّ** — تلقائي قبل كل إدراج. مفيش عامل = القديم.
5. **مهلة الانتظار (١٨٠ ثانية)** — انتهاؤها = القديم.

كلها **افتراضها مطفأ**: نشر الكود وحده لا يحوّل أي طلب.

---

## ٤. لماذا فحص العامل الحيّ هو أهم سطر في المرحلة

بدونه، فتح علم قبل نشر العامل على Railway كان يعني: كل نداء ذكاء
اصطناعي في المنصة يُدرَج في الطابور، ولا يسحبه أحد، فينتظر ثلاث دقائق
ثم يرجع للقديم. أي **تعطّل عملي كامل بسبب تبديل إعداد**.

الفحص يقرأ نبضات `queue_workers` (نافذة ١٨٠ ثانية) بذاكرة ١٥ ثانية،
ويرجع للقديم فورًا لو النوع المطلوب مش مخدوم. واللوحة كمان **ترفض فتح
علم بلا عامل**، عشان المسؤول ما يفتكرش إن النقل شغّال وهو مش شغّال.

## ٥. عامل مستقل لكل خدمة

كان عاملًا واحدًا (`WORKER_TYPE=ai`) يخدم الأحد عشر نوعًا. دلوقتي:

| نوع المهمة | نوع العامل |
|---|---|
| `ai.meeting` | `meeting` |
| `ai.discovery` | `discovery` |
| `ai.brain` | `brain` |
| `ai.prd` | `prd` |
| `ai.prototype` | `prototype` |
| `ai.qa` | `qa` |
| `ai.prompt` | `prompt` |
| `ai.support` | `support` |
| `ai.monitoring` | `monitoring` |
| `ai.knowledge` | `knowledge` |
| `ai.architecture` | `architecture` |

الفصل لأسباب تشغيلية حقيقية: **العزل** (مراجعة هندسية تسقط العملية ما
تسقطش معاها محادثة دعم ينتظرها مستخدم)، و**التوسّع المستقل**، و**حدود
الموارد** المختلفة.

الجمع لسه ممكن على بيئة صغيرة:

```bash
WORKER_TYPE=support,prompt,meeting WORKER_KEY=combo-1 npx tsx services/worker/index.ts
```

**التشغيل المحلي** يحتاج `--env-file` صراحةً: العامل عملية Node مستقلة
لا تمرّ من Next.js، فما بيقراش `.env.local` تلقائيًا. على Railway
المتغيّرات بتتحقن من المنصّة فالفرق ده ما بيظهرش هناك:

```bash
WORKER_TYPE=support WORKER_KEY=support-1 npx tsx --env-file=.env.local services/worker/index.ts
```

وعلى PowerShell (ويندوز) — مافيش بادئة متغيّرات قبل الأمر، فلازم تتحدَّد على سطرها:

```powershell
$env:WORKER_TYPE="support"; $env:WORKER_KEY="support-1"; npx tsx --env-file=.env.local services/worker/index.ts
```

## ٦. خطوات التشغيل بالترتيب

1. **تطبيق الترحيل ٠٠٧٥** يدويًا في محرّر SQL. أضِف الملف كاملًا وشغّله،
   وتحقّق:
   ```sql
   select to_regclass('public.migration_flags')       is not null as flags,
          to_regclass('public.migration_flag_events')  is not null as events,
          to_regclass('public.migration_comparisons')  is not null as comparisons;
   ```
2. **نشر عامل الخدمة الأولى** على Railway — ابدأ بـ`support` أو
   `prompt` (الأقل ترابطًا والأسرع تحقّقًا).
3. **التأكّد من ظهوره** في `/dashboard/queue`.
4. **فتح العلم ١٠٪** من `/dashboard/migration`.
5. **الانتظار حتى ٢٠ تنفيذًا على الأقل** — اللوحة ترفض الحكم قبل كده،
   لأن الحكم على ثلاث عمليات ينقلب مع أول تذبذب شبكة.
6. **قراءة الحكم**: سليم → ٥٠٪ ثم ١٠٠٪. متدهور → إطفاء وتشخيص.
7. تكرار من ٢ للخدمة التالية.

## ٧. قراءة اللوحة

- **الرجوع للقديم (`fallbacks`)** أخطر مؤشّر. كل رجوع معناه أن المسار
  الجديد **لم يعمل**، والمستخدم نجا بالقديم. تجاوز ٢٠٪ = توصية بالرجوع.
- **نسبة النجاح** أقل من القديم بأكثر من ١٠ نقاط = توصية بالرجوع.
- **البطء وحده** (ضعف زمن القديم) يُعرَض كتدهور **بلا** توصية بالرجوع:
  الترحيل ينقل الحمل خارج Vercel، وزمن أطول مقابل حمل أقل قد يكون
  مقايضة مقصودة. القرار للمشغّل.
- **«لا عيّنة»** تعني غياب بيانات، لا صفرًا. عرض الصفر هنا كان هيقرأ
  كفشل كامل وهو كذب.

## ٨. ما **لم** يُنقل — بصراحة

المواصفة طلبت نقل عشر خدمات. اللي اتبنى هو **البنية اللي بتنقلهم كلهم
دفعة واحدة**، لكن فيه حدود حقيقية لازم تتقال:

| البند | الحالة |
|---|---|
| نقل النداءات الـ٣١ | ✅ كلها تمرّ من المحوّل — بلا تعديل أي مستدعي |
| عامل مستقل لكل خدمة | ✅ ١١ نوع عامل |
| الأعلام والرجوع والقياس | ✅ مبنية ومختبَرة |
| **نقل معالجة الملفات (PDF/Word/Excel/صوت/فيديو)** | ❌ **لم يُنفَّذ.** الوسائط تُمرَّر كمرجع في الذاكرة، ونقلها يحتاج رفعًا لمخزن ثم رابطًا موقَّعًا للعامل. المحوّل بيستثنيها صراحةً ويرجّعها للقديم |
| **نقل Playwright** (مراقبة الإنتاج والتحقّق الوظيفي) | ❌ لسه بيشتغل داخل دوال Vercel |
| **الإلغاء/الاستئناف/التقدّم في واجهة المستخدم** | ⚠️ موجودة في الطابور، لكن غير مربوطة بأزرار في الواجهات — المحوّل ينتظر النتيجة تزامنيًا فيبدو للمستخدم زي القديم بالظبط. ده **مقصود**: أي تغيير في السلوك المرئي كان هيكسر شرط «ماتغيّرش أي Workflow» |
| **نقل Server Actions للأحداث** | ❌ الخدمات لسه بتنادي بعضها مباشرة؛ ناقل الأحداث (`platform_events`) موجود من ٠٠٦٣ وغير مستخدَم في السلاسل دي بعد |
| **تحسين استعلامات Supabase** (الترقيم، الأعمدة الانتقائية) | ⚠️ جزئي — استقصاء المتصفّح وحلقات N+1 اتصلّحوا في تدقيق المرحلة الأولى، لكن مراجعة شاملة لكل `select *` لم تحدث في هذه المرحلة |

النقل الحقيقي لكل خدمة على حدة (نقل منطق الأعمال نفسه للعامل بدل
تمرير برومبت جاهز) هو شغل المرحلة الخامسة. اللي اتبنى هنا هو **الطريق**
اللي بيخلّي النقل ده ممكنًا بلا مخاطرة.

## ١٠. التراجع

```sql
-- إيقاف الترحيل بلا حذف بنيته (الصحيح في ٩٩٪ من الحالات):
update public.migration_flags set state = 'off', rollout_percent = 0;
```

أو أسرع: `MIGRATION_KILL_SWITCH=on` في متغيّرات البيئة.

حذف البنية كلها: `0075_migration_control_rollback.sql` — لكنه بيمسح
سجل من غيّر أي علم ومتى، وكل بيانات المقارنة، وهما بالظبط اللي محتاجهم
لتشخيص سبب الرجوع.
