# محرّك ذكاء المعرفة والتطوّر التزايدي — المرحلة الخامسة، الجزءان الخامس والسادس

## نظرة عامة

الجزءان دول بيحوّلا مركز المعرفة من **قاعدة معرفة** إلى **مستشار أعمال
يعمل ذاتيًا**:

- **الجزء الخامس — الطبقة الاستشارية:** النظام يُفكّر فوق المعرفة
  المهيكلة، يكتشف النواقص والتعارضات والمخاطر والتحسينات، يحسب درجات
  النضج والجاهزية، ويشتغل تلقائيًا بعد أي تغيير.
- **الجزء السادس — التطوّر التزايدي:** أي معرفة جديدة تنتقل بذكاء
  للمراحل المتأثّرة فقط، بسياسة تحديث لكل موديول، بلا إعادة توليد
  المشروع كله.

**مبدأ حاكم — البناء فوق الموجود لا إعادة بنائه.** جزء كبير من المطلوب
كان مبنيًا بالفعل، وده بنى فوقه الطبقة الناقصة فقط:

| موجود بالفعل (أُعيد استخدامه) | جديد في هذين الجزأين |
|---|---|
| التعارضات (`knowledge_conflicts`) | الطبقة الاستشارية الموحّدة |
| الفجوات (`knowledge_gaps`) | درجات النضج/الجاهزية/المعمار |
| المخاطر/القرارات (0077) | فحص القدرات المؤسسية الناقصة |
| تحليل الأثر (`impact-service`) | مصفوفة الأولوية + AI Insights |
| محرّك المزامنة (`resync-engine`) | **سياسات تحديث لكل موديول** |
| `computeStaleness` | مخطّط التحديث التزايدي (delta→impact→policy) |
| التوليد الجزئي (`PrdIncrementEngine`) | مُشغّل التحليل المستمر |

## الجزء الخامس — الطبقة الاستشارية

### تقسيم العمل: حتمي مقابل ذكاء اصطناعي

القرار المعماري الأهم: **معظم القيمة تتولّد بلا نموذج**.

- **حتمي (بلا تكلفة، مضمون، متكرّر):**
  - القدرات الناقصة — فحص قوائم (`domain-checklist.ts`) على القدرات
    الحاضرة مقابل الأساسيات المؤسسية (صلاحيات، Audit، Backup، Workflow،
    Reporting، Security…) + قدرات المجال من `DOMAIN_PROFILES`.
  - التعارضات — موجودة بالفعل، تتحوّل لرؤى مباشرة.
  - الدرجات — حساب مركّب (`scoring.ts`).
- **ذكاء اصطناعي (لِما هو وحده يقدر عليه):**
  - رؤى تحليلية: أنماط معمارية، أعناق زجاجة في العمليات، مخاطر
    متوقَّعة، فرص تحسين — اللي فحص القوائم لا يكتشفها.

النموذج **ممنوع** من إعادة اكتشاف القدرات الناقصة (تُمرَّر له كسياق
محسوب)، فيركّز على التحليل لا التعداد.

### الدرجات الثلاث

| الدرجة | تجاوب على | مكوّناتها |
|---|---|---|
| **نضج المعرفة** | قد إيه فهمنا المشروع؟ | جودة + اكتمال + تغطية الأنواع + الترابط |
| **جاهزية المشروع** | قد إيه نقدر نبدأ التنفيذ؟ | تغطية المتطلبات + وضوح القدرات + حسم المخاطر + سدّ الفجوات، × معامل التعارضات |
| **جاهزية المعمار** | قد إيه المعمار واضح؟ | الكيانات/العلاقات + سير العمل + القرارات المبرَّرة + استقرار المخاطر |

**بوّابة المحتوى:** مشروع فارغ لا يستحق درجة من «غياب المشاكل». الأبعاد
المبنية على الغياب تُصفَّر بلا محتوى — «مفيش تعارضات» في مشروع فارغ ليست
جاهزية، هي فراغ.

### مصفوفة الأولوية

كل رأي يُصنَّف في ربع (قيمة × جهد): **مكسب سريع** · **مشروع كبير** ·
**وقت الفراغ** · **أعِد النظر**. ده اللي بيحوّل قائمة رؤى مسطّحة لخطة
عمل.

### Explainability و Decision Traceability

كل رأي **إلزاميًا** يحمل: `rationale` (ليه؟) + `impact` (الأثر) +
`source_refs` (المصدر). الرأي بلا أساس يُشال — «المستشار اللي بيدّي رأيًا
بلا أساس بيهلوس».

### التحليل المستمر

```
معالجة المعرفة (processNextDomain)
        │  processed > 0
        ▼
 triggerIntelligence  ← فيه عامل knowledge_intelligence حيّ؟
        ├── أيوه ─→ الطابور (نفس قفل المشروع)
        └── لأ ──→ runIntelligence مباشرةً
```

نفس درس المرحلة الرابعة: **لو مفيش عامل حيّ، الطابور حفرة** — فالحارس
موجود، والرجوع للمباشر مش تراجعًا.

## الجزء السادس — التطوّر التزايدي

### الفلسفة

«إذا أضاف المستخدم ملفًا واحدًا أو Policy جديدة، لا تُعِد تشغيل كل
المراحل. حلّل الجديد فقط، واكتشف ما المراحل المتأثرة.»

### المخطّط: delta → impact → policy

`plan-update.ts` (نقي) بيربط ثلاث حقائق:

1. **الدلتا** — أي نوع معرفة اتغيّر؟ (`KnowledgeChangeType`)
2. **الأثر** — خريطة حتمية `CHANGE_IMPACT`: أي موديولات تتأثّر.
3. **السياسة** — لكل موديول: تلقائي / موافقة / أبدًا.

مطابق لمثال المواصفة:

```
Requirement → Brain → PRD → Prompt        (لا يؤثّر على العرض/التسليم)
Policy      → Brain → Architecture         (لا يؤثّر على Prototype)
```

النتيجة **خطة تحديث** بثلاثة أقسام: تحديث تلقائي / بانتظار موافقة /
متخطّى — بدل إعادة توليد المشروع كله.

### سياسات التحديث لكل موديول

الفجوة الوحيدة الحقيقية في الجزء السادس: اليوم فيه **مفتاح عام واحد**
(`brain_settings.auto_resync_downstream`). ده وسّعه لتحكّم **لكل
موديول** عبر `knowledge_update_policies` (auto_update / manual_approval
/ never). الموديول الغائب = الافتراضي (موافقة يدوية — أأمن سلوك).

### إعادة استخدام البنية القائمة

| القدرة المطلوبة | مبنية بالفعل في |
|---|---|
| كشف التغيير + إعادة المزامنة | `notifyBrainChanged` (`resync-engine.ts`) |
| الأثر/الاعتماد | `computeStaleness` + `impact-service` |
| التوليد الجزئي (قسم PRD فقط) | `PrdIncrementEngine` + `PRD_INCREMENT_SECTION` |
| الموافقة/الدمج/التعارض | `pending-changes-service` + `conflict-engine` |
| الإصدارات + التراجع | `repository.ts` + `*_versions` لكل نطاق |
| سجلّ التغيير + الخط الزمني | `audit-trail/timeline-service.ts` |
| الإشعارات | `notifications/reconcile-service.ts` |

الطبقة الجديدة **تنسّق** فوق دي، لا تستبدلها.

## ثغرات معلومة — بصراحة

| البند | الحالة |
|---|---|
| ربط الرؤى بمسار توليد تلقائي | ⚠️ الرؤى تُولَّد وتُعرَض؛ تنفيذها قرار بشري (لا تنفيذ تلقائي بعد) |
| لوحة AI Insights كاملة (مصفوفة الأولوية المرئية) | ⚠️ البيانات والإجراءات جاهزة؛ لوحة العرض المخصّصة تُبنى فوقها |
| ربط `planUpdate` بمسارات التغيير الفعلية | ⚠️ المخطّط والسياسات جاهزان؛ استدعاؤهما من كل مسار كتابة خطوة تالية |
| إشعار عند رأي حرج جديد | ⚠️ عبر reconcile القائم — يحتاج مصدر مرشّح جديد |

كلها **قدرات تُبنى فوق الأساس**، لا حواجز فيه.
