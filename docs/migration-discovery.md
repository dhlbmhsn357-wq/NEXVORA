# منصّة اكتشاف الترحيل وذكاء المصادر — Migration Discovery & Source Intelligence

المرحلة ١ من **Migration Intelligence Platform**. ليست ميزة استيراد بيانات،
بل منصّة ذكاء تفهم أي نظام قديم بالكامل **قبل** أي ترحيل.

> **الفلسفة: Understand Before Migrate.** هذه المرحلة لا تنقل أي بيانات —
> تبني المرجع الرسمي الذي تُبنى عليه مراحل الترحيل الثماني التالية.

## القرار المعماري الأمني (الأساس)

الاحتفاظ بكلمات مرور قواعد بيانات إنتاج للعملاء وفتح اتصالات صادرة من
خادم serverless هو الأخطر أمنيًا، ودرايفرات Oracle/SQL Server الـnative
تكسر بناء Vercel. لذلك:

| وضع الاتصال | الحالة | الأمان |
|---|---|---|
| **رفع ملف** (CSV/JSON) | ✅ حيّ اليوم | بلا بيانات اعتماد |
| **رفع بنية** (Schema Dump/DDL) | ✅ حيّ اليوم | **الأأمن لقواعد الإنتاج** — العميل يصدّر البنية فقط |
| **اتصال حيّ مباشر** | ⏸️ معرَّف كواجهة، مؤجَّل | يُنفَّذ عبر طبقة اتصال معزولة لاحقًا |

أي سرّ يُخزَّن **مشفَّرًا AES-256-GCM** (`lib/security/secret-crypto.ts`،
مفتاح من `MIGRATION_SECRET_KEY`) — لا نصّ صريح، لا يُعاد للعميل، لا يُسجَّل.

## تدفّق الاكتشاف

```
تسجيل مصدر → اختبار الاتصال/الصلاحية
        ↓
محتوى (ملف/DDL) → parseSourceContent → بنية مُطبَّعة
        ↓
analyzeSchema (حتمي بالكامل):
  ├─ الكشف الدلالي   (customers/crm_client → كيان Customer)
  ├─ العلاقات        (parent_child / M2M / recursive / broken / missing)
  ├─ الاعتماديات     (حرجة / أساسية / مشتركة / غير مستخدمة / ميتة + دورات)
  ├─ الجودة          (اكتمال / اتساق / سلامة / بنية)
  ├─ المخاطر         (FK مكسور / دورات / بلا مفتاح / أنواع معقّدة / ضخمة)
  ├─ تدفّق الأعمال    (Customer→Order→Invoice→Payment...)
  └─ الجاهزية         (/100 مع تفسير + قائمة مراجعة بشرية)
        ↓
تهذيب الذكاء الاصطناعي (اختياري — فوق التحليل الجاهز، لا يخترع)
        ↓
migration_reports (المرجع الرسمي لمراحل الترحيل التالية)
```

## الفصل المعماري: حتمي أولًا، ذكاء اصطناعي فوقه

كل الفهم (كيانات/علاقات/جودة/مخاطر/جاهزية) **حتمي بالكامل** — نفس المدخل
يعطي نفس المخرَج، قابل للاختبار بلا شبكة. الذكاء الاصطناعي يضيف **طبقة
تفسير بشرية فقط** (نوع النظام، سرد المخاطر، ما يحتاج مراجعة) وممنوع عليه
اختراع جداول أو أرقام غير موجودة في التحليل. لو غاب الذكاء الاصطناعي،
التحليل الحتمي كافٍ وحده.

## الكشف الدلالي (Semantic Detection)

لا يعتمد على أسماء الجداول حرفيًا. `tbl_customer / clients / crm_client /
customers` كلها → كيان **Customer** واحد، عبر قاموس مرادفات (عربي/إنجليزي)
+ تسجيل + تجريد الجمع والبادئات الضوضائية (`tbl_`, `sys_`...). كل كيان
مصنَّف: master / reference / transactional / configuration / audit / log.

## التكامل مع طبقات المعرفة

نتائج الاكتشاف **معرفة جديدة، لا ترحيل**. بموافقة المدير، يُرقّى تحليل
النظام إلى **مرشّح خبرة مؤسسية** (`org_experience_candidates`، الجزء X)
— منظَّف، عام، قابل لإعادة الاستخدام — يمرّ بنفس حاجز المراجعة البشرية
القائم قبل دخول المكتبة. فتستفيد المشاريع القادمة من كل نظام قديم حُلِّل.

## الصلاحيات

| الدور | القدرة |
|---|---|
| **Director/Admin** | إنشاء/تعديل/اختبار/تحليل/حذف/ترقية |
| **Supervisor** | قراءة فقط |
| **Executor** (member) | لا يرى هذه المرحلة (مخفيّة في التنقّل + محروسة في الإجراءات) |

## الأداء

التحليل الحتمي يعمل على البنية (لا صفوف البيانات) فهو سريع. يعمل في الخلفية
عبر `after()` مع حالة على `migration_snapshots` تقرأها الواجهة. البنية جاهزة
للتحليل على دفعات مع الاستئناف (`progress`/`checkpoint`) لأي مصدر ضخم
مستقبلًا عبر طابور المهام القائم.

## ثغرات معلومة — بصراحة

| البند | الحالة |
|---|---|
| الاتصال الحيّ المباشر (Postgres/MySQL/Mongo...) | ⏸️ معرَّف كواجهة؛ يُفعَّل عبر طبقة اتصال معزولة (لا يحتفظ الخادم بكلمات مرور إنتاج) |
| تحليل Excel/XML/YAML الثنائي | ⏸️ CSV/JSON/DDL حيّ؛ البقية تُضاف عند الحاجة (بلا كسر البناء) |
| قراءة صفوف حقيقية لجودة على مستوى القيمة | ⏸️ الجودة البنيوية جاهزة؛ فحص القيم يتطلّب طبقة الاتصال الحيّ |
| التحليل على دفعات لقواعد ضخمة جدًا | ⏸️ البنية جاهزة (progress/checkpoint)؛ يُوصَل بالطابور عند وجود اتصال حيّ |

كلها **قدرات تُبنى فوق أساس مكتمل ومختبَر**، لا حواجز فيه. المرحلة تنتج
المرجع الرسمي الذي تعتمد عليه مراحل الترحيل الثماني القادمة.
