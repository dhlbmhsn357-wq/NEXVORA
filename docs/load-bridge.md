# جسر الحمل — Load Bridge (إغلاق فجوة الضخّ)

يُكمِل محرّك الترحيل الحقيقي (المرحلة ٦ / 0088). قبله كان المحرّك يُحوّل
الصفوف ويتحقّق منها ويحسبها ثم **يُهملها**؛ الآن يُثبّتها ويُصدّرها بصيغة
جاهزة للاستيراد، مع مطابقة أعداد ووجهات حمل.

## ما الذي أغلقه بالضبط

| قبل | بعد |
|---|---|
| `executeChunk` يُنتج الصفوف المُحوَّلة (`loaded`) ثم تُهمَل | تُثبَّت في `migration_loaded_datasets` عند اكتمال الترحيل |
| لا مخرجات قابلة للاستيراد | حزمة SQL/CSV/JSON قابلة للتنزيل بترتيب التبعية |
| لا مطابقة بعد التحويل | مطابقة أعداد لكل كيان (المتوقَّع من التنفيذ = المُثبَّت) |
| لا مفهوم «وجهة» | وجهات حمل (ملف تصدير / اتصال مباشر) مع أسرار مُشفَّرة |

## المعمار — `lib/load-bridge/`

**نواة نقيّة (بلا I/O، مُختبَرة):**
- `serializers.ts` — CSV/JSON/SQL INSERT مع هروب آمن (يمنع كسر الملف وحقن SQL).
- `reconciliation.ts` — مطابقة الأعداد + بصمة FNV-1a + بناء البيان.
- `target-adapters.ts` — سجلّ أنواع الوجهات + التحقّق من الإعداد.
- `load-types.ts` — الأنواع.

**خدمات (I/O):**
- `dataset-service.ts` — `persistLoadedDatasets` (يُعيد اشتقاق المخرجات
  حتميًّا ويُثبّتها؛ آمن للاستئناف) · `loadDatasetRows`.
- `load-package-service.ts` — `buildLoadPackage` (يقرأ المُثبَّت، يُسلسل
  بترتيب التبعية، يجمع في حزمة، يُطابق الأعداد، يرفع artifact + رابط موقّع).
- `target-service.ts` — CRUD وجهات مع تشفير الأسرار (نفس نمط 0083).
- `load-run-service.ts` — يختار المسار: تصدير ملف أو حمل مباشر.
- `dashboard.ts` · `notify.ts`.

## المسار العملي

اكتمل الترحيل (P6) → تُثبَّت المخرجات تلقائيًّا → في لوحة «الترحيل
الحقيقي» تظهر لوحة **جسر الحمل**: اختر الصيغة (SQL/CSV/JSON) و«ابنِ حزمة
الحمل» → تنزيل + تقرير مطابقة. اختياريًّا عرّف وجهة (Postgres/REST) للحقن
المباشر عبر موصّل النشر.

## قاعدة البيانات (0091)

| الجدول | الغرض |
|---|---|
| `migration_loaded_datasets` | المخرجات المُحوَّلة المُثبَّتة لكل كيان |
| `migration_load_targets` | وجهات الحمل (أسرار مُشفَّرة) |
| `migration_load_runs` | عمليات الحمل + المطابقة + مفتاح الحزمة |

## موصّلات الحمل المباشر — `connectors.ts`

كتابة فعلية في نظام الهدف (بلا مكتبات جديدة):

- **REST API** — عبر `fetch` القياسي. يدفع دفعات لكل كيان (`{entity}` في
  الـURL)، ترويسة مصادقة (Bearer/apikey/none)، شكل جسم (array/wrapped)،
  إعادة محاولة مع تراجع أُسّي، والتقاط أخطاء لكل دفعة. **يمرّ عبر منطق
  أعمال الـ ERP — الأأمن.**
- **Supabase** — عبر `@supabase/supabase-js` الموجود: insert/upsert مباشر
  على قاعدة الهدف، على دفعات، مع `onConflict` اختياري.

المطابقة تُحسب من **الأعداد المكتوبة فعليًّا** (لا المصدَّرة): `completed`
لو طابقت، `partial` لو فشل بعضها، `failed` لو لم يُكتب شيء — بصراحة.

## حدود صادقة

| البند | الحالة |
|---|---|
| تصدير SQL/CSV/JSON قابل للتنزيل | ✅ يعمل اليوم لأي ERP يقبل استيراد ملف |
| حقن مباشر REST API | ✅ حقيقيّ عبر fetch (ينشط عند إضافة endpoint + token) |
| حقن مباشر Supabase/Postgres للهدف | ✅ حقيقيّ عبر العميل الموجود (ينشط عند إضافة url + service key) |
| اتصال Postgres خام (connection string) | ⏸️ يحتاج موصّل نشر معزول (Vercel serverless لا يناسب الاتصالات الطويلة)؛ حتى ذلك تُبنى حزمة تصدير كبديل |
| المخرجات تُشتقّ من العيّنة المُقدَّمة | ✅ حتميّ؛ يطابق ما رحّله المحرّك |
