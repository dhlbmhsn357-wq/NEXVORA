PM Operating System — تدقيق واجهة قبل إعادة التصميم

مراجعة فعلية للكود الحالي (مش تقييم عام) — أرقام حقيقية من فحص كل ملفات app/*.tsx، لتحديد إيه اللي محتاج فعليًا يتحسّن قبل أي إعادة بناء، وإيه اللي مطلوب في برومبت الـ Redesign الأصلي بس مش مبرر لحجم VELORA الفعلي (فريق داخلي ~10، عملاء محدودين).

الحكم العام

الواجهة الحالية متسقة بصريًا بشكل معقول (نفس النظام اللوني، نفس الخط) لكنها مبنية بأسلوب "انسخ والصق" لا نظام — كل لوحة بتعيد كتابة نفس الزرار والكارت والمودال بصياغة شبه متطابقة بدل استخدام مكوّن مشترك. المشكلة الحقيقية مش "شكل قديم"، المشكلة إنه مفيش Design System فعلي خلف الشكل الموجود — وده بالظبط اللي المفروض يتحل الأول قبل أي تجميل بصري.

Design Tokens — الموجود فعليًا

فحص app/globals.css الفعلي بالكامل — مش افتراض.

الخبر الجيد: فيه فعلًا نظام ألوان مركزي (CSS Variables) مطابق لموقع VELORA الحقيقي — مش لون Hardcoded من الصفر. ده أساس ممتاز نبني عليه، مش نبدأ منه من جديد.

مفيش Spacing Scale أو Radius Scale أو Shadow Scale — كل قيمة بتتكتب يدوي

كل رقم (px-4, py-2, rounded-lg, shadow) بيتكرر يدويًا في كل ملف بدل ما يبقى Token واحد. النتيجة: مفيش طريقة تضمن إن كل الأزرار بنفس الـ Radius غير المراجعة اليدوية لكل ملف (زي ما الأرقام فوق بتوضح).

مفيش Typography Scale مسمّى (H1-H4, Body, Caption) — بس Tailwind utilities خام

text-2xl, text-sm, text-xs منتشرين بدون تسلسل هرمي واضح موثّق. النتيجة: عنوان صفحة في مكان ممكن يبقى نفس حجم عنوان قسم في مكان تاني.

صفر Dark Mode فعلي — رغم إن Tailwind v4 و@theme inline بيدعموه بسهولة

مفيش @media (prefers-color-scheme: dark) ولا data-theme في globals.css خالص.

03

Typography

خط واحد فقط (Tajawal) بوزنين فعليين مُستخدمين (400 عادي، 800 .font-display)

مقبول تمامًا لهوية VELORA (مش عيب)، لكن غياب مستويات وسطى (600 لعناوين الأقسام) بيخلي التسلسل الهرمي البصري ضعيف أحيانًا — كل حاجة إما عادي جدًا أو Bold جدًا.
04

Spacing وRadius

rounded-lg (8px) وrounded-xl (12px) بيتستخدموا بالتبادل على عناصر من نفس النوع

مثال حقيقي: أزرار الـ Primary الكبيرة بتستخدم rounded-lg، بينما الكروت اللي بتحويها بتستخدم rounded-xl — مفيش قاعدة واضحة "الأزرار = كذا، الكروت = كذا".
05

الموبايل والاستجابة

Top Navigation (app/dashboard/layout.tsx) بلا أي معالجة للموبايل — صفر Drawer، صفر Hamburger

الروابط السبعة (نظرة عامة، عملاء محتملون، عملاء، مشاريع، الإعدادات، دليل الاستخدام...) في flex items-center gap-5 واحد بدون flex-wrap ولا نسخة موبايل — على شاشة 375px هتتقطع أو تعمل Scroll أفقي غير مقصود.

استخدام Breakpoints محدود جدًا (12 ملف بس من ~60) — الجداول ومعظم الكروت بلا نسخة موبايل مخصصة

Support Requests وLeads/Projects lists بتعرض جداول/كروت بعرض ثابت نسبيًا؛ تشتغل لكن مش محسّنة للمس أو الشاشات الصغيرة فعليًا.
لكن بصراحة: السؤال الحقيقي قبل أي استثمار هنا: هل فريقك الداخلي (10 أشخاص) بيستخدم النظام من الموبايل أصلًا؟ لو الإجابة "نادرًا"، الأولوية الصح هي إصلاح الـ Overflow في الـ Top Nav بس (High)، مش Redesign كامل Mobile-First من 360px (اللي البرومبت الأصلي طلبه) — ده مجهود كبير لسيناريو استخدام نادر.
06

إمكانية الوصول

90 عنصر <button> في الكود، 32 بس عندهم focus-visible:outline صريح

الباقي بيعتمد على الـ Focus Ring الافتراضي للمتصفح (شغّال فعليًا، بس شكله غير متسق مع الأزرار اللي مخصص لها Style).

استخدام aria-* موجود بس محدود (18 ملف) — أغلبه aria-expanded وaria-modal بس، بدون aria-label على أزرار الأيقونات (زي 📎 في الـ Widget)

07

Loading وAnimation

Skeleton موجود جزئيًا (5 صفحات loading.tsx + Skeletons داخلية في بعض اللوحات) — مش شامل لكل الحالات

3 مواضع بس لسه بتستخدم نص "جاري التحميل…" عادي بدل Skeleton بصري.

صفر مكتبة Animation (Framer Motion مش موجودة، ولا أي حركة CSS منظمة) — الانتقالات محصورة في transition Tailwind البسيطة (hover fade)

شغّال ومحترم، بس بلا حركات دخول/خروج للـ Modals أو الكروت.
08

الملاحة والهيكل العام

مفيش Breadcrumbs، مفيش بحث عام (Global Search)، مفيش مركز إشعارات

مقبول جزئيًا لحجم النظام الحالي (عدد الصفحات محدود)، لكن مع نمو عدد المشاريع (بعد ما عملنا Pagination) البحث العام هيبقى مفيد فعليًا.

تبويبات المشروع (10 تبويبات دلوقتي بعد إضافة Activity) بتفضل في صف واحد flex-wrap — شغّالة لكن هتبقى مزدحمة بصريًا مع أي تبويب جديد
