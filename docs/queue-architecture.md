# بنية الطوابير والعمال — دليل المرحلة الثانية

**الحالة:** بنية تحتية مكتملة · لم يُنقل أي منطق أعمال · لم يُنشر شيء

---

## ١. الغرض والحدود

هذه الطبقة تمنع تنفيذ أي عملية ثقيلة داخل Next.js أو Vercel أو مسارات
الواجهة أو الإجراءات، وتحوّلها إلى مهام خلفية تعمل داخل عمال Railway.

**ما نُفِّذ:** الطابور، وآلة الحالة، والأولويات، وإعادة المحاولة،
والرسائل الميتة، والأقفال الموزّعة، وIdempotency، والإلغاء، والاستئناف،
والتقدّم، والسجلات، ولوحة المشغّل، وإطار العمال، والمجدوِل، والأحداث،
والمقاييس، وفحوص الصحة.

**ما لم يُنفَّذ عن قصد:** لم يُنقل أي ذكاء اصطناعي، ولا تليجرام، ولا
مركز المعرفة، ولا Project Brain، ولا المراجعة الهندسية. ولم يُعدَّل أي
منطق أعمال قائم، ولم تُحذف أي ميزة.

## ٣. دورة حياة المهمة

```
 pending ──► queued ──► running ──► completed
              ▲  │         │
              │  │         ├──► retrying ──► queued   (فشل عابر)
              │  │         ├──► timeout  ──► retrying (تجاوز المهلة)
              │  │         ├──► failed   ──► dead_letter
              │  │         └──► paused   ──► queued
              │  └──► waiting (قفل محجوز أو موعد لم يحن)
              └──────────────┘

 canceled ◄── من: pending · queued · waiting · running · retrying · paused · timeout
```

### تمييزان يستحقان الشرح

**`waiting` مقابل `queued`.** الأولى محجوبة بشرط خارجي (قفل مورد محجوز
أو موعد مجدول)، والثانية جاهزة الآن. الخلط بينهما يخفي سبب التأخير،
فيرى المشغّل طابورًا طويلًا دون أن يعرف أن نصفه ليس جاهزًا أصلًا.

**`timeout` مقابل `failed`.** الأولى «لم تنتهِ في وقتها»، والثانية «رمت
خطأ». القياسان مختلفان والعلاج مختلف: المهلة تقول إن الميزانية الزمنية
صغيرة، والخطأ يقول إن هناك عطلًا.

### ثابت بنيوي مُختبَر

مستحيل أن تعود مهمة في حالة نهائية إلى التنفيذ. الاختبار يمشي على كل
المسارات الممكنة من كل حالة نهائية ويؤكد أن أيًّا منها لا يصل إلى
`queued` أو `running`. بدون هذا الثابت، مهمة فاشلة قد تدور بلا نهاية.

## ٤. الأولويات

| الأولوية | الاستخدام |
|---|---|
| `critical` | تفاعلي — المستخدم واقف ينتظر |
| `high` | طلبها المستخدم صراحة ثم تركها |
| `normal` | نتجت عن حدث (تتالٍ) |
| `low` | تحليل ثقيل غير عاجل |
| `background` | صيانة دورية |

**الحماية من التجويع:** أي مهمة انتظرت أكثر من ساعة تُرقّى درجة، ودرجة
إضافية لكل ساعة بعدها. بدون هذه القاعدة تبقى مهام `background` في الطابور
إلى الأبد — وهذا ليس احتمالًا نظريًا: مهمة مجدولة كل ربع ساعة كفيلة
بتجويعها دائمًا.

**الضغط العكسي:**

| عمق الطابور | السلوك |
|---|---|
| أقل من ٥٠٠ | قبول كامل |
| ٥٠٠ – ٢٠٠٠ | رفض `low` و`background` برسالة واضحة |
| أكثر من ٢٠٠٠ | `critical` فقط |

## ٥. إعادة المحاولة

```
التأخير = min(٢ ثانية × ٢^المحاولة، ٥ دقائق) ± ٢٠٪ عشوائية
```

**العشوائية ليست تجميلًا.** بدونها تعيد كل المهام التي فشلت في نفس
اللحظة المحاولةَ في نفس اللحظة بالضبط، فيتكرّر الانهيار الذي أوقعها.

**تصنيف الفشل إلزامي:**

| الفئة | أمثلة | السلوك |
|---|---|---|
| `transient` | ٤٢٩ · مهلة · ٥٠٣ · انقطاع اتصال | إعادة محاولة مع تراجع |
| `permanent` | ٤٠٠ · ٤٠٣ · مدخل غير صالح | **بلا إعادة محاولة** — رسائل ميتة فورًا |
| `unknown` | غير مصنّف | محاولتان ثم رسائل ميتة |

الترتيب داخل التصنيف مقصود: الدائم يُفحص أولًا، لأن رسائل الأخطاء
الحقيقية تخلط الكلمات — و«٤٠٠ invalid timeout parameter» يجب أن يُقرأ
خطأً دائمًا لا عابرًا لمجرد وجود كلمة «timeout» فيه.

## ٦. الرسائل الميتة

المهمة التي تستنفد محاولاتها تُنقل إلى `job_dead_letters` و**لا تُحذف
أبدًا**. لوحة المشغّل تعرضها مع الخطأ النهائي وتتيح إعادة الإدراج بعد
إصلاح السبب.

إعادة الإدراج تنشئ **مهمة جديدة** لا تُحيي القديمة: التاريخ يبقى محفوظًا
كاملًا والفشل القديم يظل قابلًا للمراجعة.

> الطابور الصامت الممتلئ بالفشل أسوأ حالة ممكنة: نظام يبدو سليمًا وهو لا
> ينجز شيئًا. ولهذا أي دخول للرسائل الميتة يرفع حالة النظام إلى «متدهور».

## ٧. الأقفال الموزّعة

`SKIP LOCKED` يمنع سحب نفس **المهمة** مرتين. لكنه لا يمنع مهمتين
**مختلفتين** من الكتابة في نفس المورد معًا — مثل إعادتَي توليد لنفس
Brain.

القفل هنا بالمورد لا بالمهمة:

```ts
lockKey: (payload) => `brain:${payload.projectId}`
```

يُحجز داخل نفس معاملة المطالبة (فلا سباق)، وله انتهاء صلاحية، ويُحرَّر
عند الاكتمال والفشل والإلغاء. القفل الذي لا يُحرَّر عند الفشل يحجب
المورد إلى الأبد.

## ٨. منع التكرار — آليتان مختلفتان

| | إسقاط التكرار | Idempotency |
|---|---|---|
| **يحمي من** | الضغط المتكرر على زر خلال ثوانٍ | إعادة المحاولة الشبكية بعد ساعة |
| **المفتاح** | بصمة محسوبة من الحمولة | مفتاح يولّده العميل |
| **النطاق** | المهام الحيّة فقط | ٢٤ ساعة، حتى بعد الاكتمال |
| **بعد الانتهاء** | نفس المدخل ينشئ مهمة جديدة | يرجّع النتيجة المحفوظة |

الاثنان مطلوبان: بعد اكتمال التوليد، إعادة التوليد بنفس المدخل **عملية
مشروعة** يجب أن تُقبل — بينما إعادة إرسال نفس الطلب الشبكي **يجب** أن
ترجّع النتيجة القديمة.

**حارس أمان:** نفس مفتاح Idempotency ببصمة مدخل مختلفة = خطأ صريح، لا
تنفيذ صامت. هذا يكشف أخطاء العميل بدل إخفائها.

## ٩. الإلغاء والاستئناف

**الإلغاء** يُفحص **بين الخطوات لا أثناءها**. الإلغاء وسط نداء مدفوع
الثمن (نموذج ذكاء اصطناعي) يرمي عملًا دُفع فيه فعلًا. وإشارة
`AbortSignal` تُرفع أيضًا، فأي نداء يدعمها يتوقف فورًا.

**الاستئناف** يعتمد على `checkpoint` لا على `progress`:

```ts
await ctx.saveCheckpoint({ chunksDone: 40 });
// بعد الفشل والاستئناف:
const startAt = ctx.checkpoint?.chunksDone ?? 0;
```

`progress` رقم للعرض فقط. الاستئناف بناءً عليه يعني حساب موضع التوقّف
من نسبة مئوية — تقريب يفقد بيانات.

## ١٠. إضافة عامل جديد — الوعد المعماري

**ملف واحد + سطر استيراد. لا شيء غير ذلك.**

```ts
// lib/queue/handlers/knowledge.ts
import { defineJobHandler } from "../registry";

defineJobHandler<{ projectId: string; sourceId: string }>({
  type: "knowledge.classify",
  workerType: "knowledge",
  concurrency: 5,
  timeoutMs: 120_000,
  maxAttempts: 3,
  defaultPriority: "high",
  lockKey: (p) => `knowledge:${p.projectId}`,
  dedupeHash: (p) => `classify:${p.sourceId}`,
  allowedRoles: ["member"],
  requiresProjectMembership: true,
  handler: async (ctx) => {
    const startAt = (ctx.checkpoint?.index as number) ?? 0;
    for (let i = startAt; i < chunks.length; i++) {
      if (await ctx.isCanceled()) return;
      // … العمل الحقيقي …
      await ctx.saveCheckpoint({ index: i + 1 });
      await ctx.reportProgress(Math.round(((i + 1) / chunks.length) * 100));
    }
    return { result: { classified: chunks.length } };
  },
});
```

```ts
// lib/queue/handlers/index.ts
import "./system";
import "./knowledge";   // ← السطر الوحيد المضاف
```

```bash
WORKER_TYPE=knowledge WORKER_KEY=knowledge-1 npx tsx services/worker/index.ts
```

**لم يُلمس:** الطابور، ووقت تشغيل العامل، وقاعدة البيانات، واللوحة،
والمقاييس. كلها تكتشف النوع الجديد من السجل تلقائيًا.

## ١١. تشغيل العامل

```bash
WORKER_TYPE=system \
WORKER_KEY=system-1 \
WORKER_CONCURRENCY=5 \
RUN_SCHEDULER=true \
npx tsx services/worker/index.ts
```

| المتغيّر | الوصف |
|---|---|
| `WORKER_TYPE` | **مطلوب** — يحدّد الأنواع التي يخدمها |
| `WORKER_KEY` | معرّف النسخة (يُشتقّ تلقائيًا لو غاب) |
| `WORKER_CONCURRENCY` | أقصى مهام متزامنة |
| `RUN_SCHEDULER` | `true` على نسخة **واحدة فقط** |

**سلوكيات مبنية في وقت التشغيل:**

- عامل بلا أنواع مسجّلة **يرفض الإقلاع** بخطأ صريح. عامل يدور فارغًا
  إلى الأبد يبدو سليمًا في كل المقاييس — وهو أسوأ أنواع الأعطال.
- المهلة تُنفَّذ كإلغاء لا كقطع، فالمعالج يأخذ فرصة للتنظيف.
- الإيقاف الآمن ينهي الجاري ويُبقي النبضة حتى النهاية.
- الاستثناء غير الملتقَط يُنهي العملية عمدًا: Railway يعيد التشغيل،
  وآلية التعافي تلتقط المهام.

## ١٢. قاعدة البيانات

| الجدول | الغرض |
|---|---|
| `jobs` | الجدول المركزي — كل الحقول المطلوبة في المواصفة |
| `job_events` | سجل الانتقالات، غير قابل للتعديل |
| `job_logs` | تنفيذ · تحذير · خطأ · أداء |
| `job_dead_letters` | الأرشيف القابل للمراجعة |
| `job_locks` | الأقفال بالمورد مع انتهاء صلاحية |
| `job_idempotency_keys` | المفاتيح والردود المحفوظة (٢٤ ساعة) |
| `queue_workers` | التسجيل والنبضة والصحة |
| `queue_metrics` | التتبّع التاريخي |

**الدوال:**

| الدالة | الغرض |
|---|---|
| `claim_next_job` | مطالبة ذرّية بـ `for update skip locked` + حجز القفل |
| `recover_stuck_jobs` | استعادة ما تجاوزت نبضته المهلة + تنظيف الأقفال اليتيمة |
| `promote_scheduled_jobs` | ترقية المؤجَّلة التي حان وقتها |
| `queue_stats` | إحصاءات في استعلام واحد |

**الفهرس الأهم** — جزئي عن قصد:

```sql
create index idx_jobs_claim on jobs (priority, available_at, created_at)
  where status = 'queued';
```

المهام المنتهية تمثّل الأغلبية الساحقة بعد شهور، وإدخالها في الفهرس
يُبطّئ كل مطالبة بلا فائدة.

**لماذا الدوال في القاعدة لا في التطبيق؟** عميل Supabase يتحدث عبر
PostgREST ولا يستطيع تنفيذ `for update skip locked`. والقراءة ثم التحديث
من التطبيق تسمح لعاملين بأخذ نفس الصف — وهذا بالضبط ما تمنعه المطالبة
الذرّية.

**التراجع:** `0073_job_queue_rollback.sql` كامل ومرتّب (الأبناء ثم
الدوال ثم الأنواع). الترحيل إضافي بالكامل ولم يمسّ أي جدول قائم.

## ١٣. نتائج القياس

المقاسة على المحاكي في الذاكرة، بمهام فارغة، بأولويات مختلطة:

| الحجم | الإدراج | معدّل الإدراج | التصريف | معدّل التصريف |
|---|---|---|---|---|
| ١٠٠ | ١.١٤ م.ث | ٨٧,٧٦٥/ث | ٧.٠١ م.ث | ١٤,٢٦٨/ث |
| ٥٠٠ | ٠.٨٢ م.ث | ٦٠٧,٠١٧/ث | ١٣٣.٨٩ م.ث | ٣,٧٣٤/ث |
| ١,٠٠٠ | ١.٤٤ م.ث | ٦٩٥,٩٤٣/ث | ٤٩٣.٢٧ م.ث | ٢,٠٢٧/ث |
| ٥,٠٠٠ | ٦.٨٨ م.ث | ٧٢٦,٤٨٠/ث | ٩,٢٦٨.٦٧ م.ث | ٥٣٩/ث |

ترتيب ٥,٠٠٠ مهمة بالأولوية والتقادم: **١٢ مللي ثانية**.

### قراءة الأرقام بأمانة

**الإدراج خطّي وسريع جدًا** — أكثر من ٧٠٠ ألف عملية في الثانية عند
٥,٠٠٠. منطق الإدراج (Idempotency، إسقاط التكرار، بناء الصف) رخيص فعليًا.

**منحنى التصريف تربيعي، وهذا عيب في المحاكي لا في التصميم.** دالة
`claim` في المحاكي تمسح كل المهام وترتّبها في **كل** نداء. المسار
الإنتاجي يستخدم فهرسًا جزئيًا في PostgreSQL:

```sql
create index idx_jobs_claim on jobs (priority, available_at, created_at)
  where status = 'queued';
```

فيعيد الصف التالي مباشرة بتعقيد لوغاريتمي لا تربيعي. الفرق بين ٥٣٩/ث
هنا وبين الأداء الحقيقي فرقُ **تنفيذ المحاكي**، لا فرقُ تصميم.

**ملاحظة منهجية على الأرقام السابقة:** القياس الأول كان بالضغط العكسي
مفعَّلًا، فكان «٥,٠٠٠ مهمة» يُنشئ ٢,٠٠٠ فعليًا لأن المنخفضة تُرفض بعد
العتبة — رقم مضلِّل. الضغط العكسي مطفّأ في القياس الآن، والأرقام أعلاه
لخمسة آلاف مهمة حقيقية.

**ما تثبته هذه الأرقام:** أن منطق الطابور نفسه (الترتيب، الأولويات،
إسقاط التكرار، قرارات إعادة المحاولة) رخيص جدًا — عشرات إلى مئات الآلاف
من العمليات في الثانية، وهو أعلى بمراتب من أي حمل متوقَّع.

**ما لا تثبته:** أداء PostgreSQL، وسلوك `SKIP LOCKED` تحت تزامن حقيقي،
وزمن الشبكة، وتكلفة الفهارس عند ملايين الصفوف. هذه تحتاج قياسًا على
قاعدة حقيقية بعد تطبيق الترحيل — **وهي ليست جزءًا من نتائج هذه المرحلة**.

**تحقّق من الصحة عند الحجم:** ١,٠٠٠ مهمة و٢٠ عاملًا متزامنًا = صفر
معالجة مزدوجة، وكل مهمة نُفِّذت مرة واحدة بالضبط.

### قياس على قاعدة البيانات الحقيقية

نُفِّذ بعد تطبيق الترحيل، من جهاز خارج منطقة القاعدة (المرجع: **١٣٨
مللي ثانية** لأبسط استعلام ممكن — `select id limit 1`).

| العملية | قبل | بعد | التحسين |
|---|---|---|---|
| المطالبة (م٥٠) | ٣٨٠ م.ث | **٢٥٩ م.ث** | −٣٢٪ |
| المطالبة (م٩٥) | ٤٤٣ م.ث | **٢٩٦ م.ث** | −٣٤٪ |
| الإدراج (م٥٠) | ٦٤٩ م.ث | **٥١٨ م.ث** | −٢٠٪ |
| تصريف ١٠٠ مهمة | ٩٤.٦ ث | **٦٨.٣ ث** | −٢٨٪ |

**ما كشفه القياس:** الزمن كان **رحلات شبكة لا عمل قاعدة بيانات**.
٦٤٩ م.ث للإدراج ÷ ١٣٨ م.ث للرحلة = خمس رحلات متتالية. والفحوص كانت
مستقلة تمامًا وتُنفَّذ بالتسلسل بلا سبب.

**الإصلاح:** توازي الاستدعاءات المستقلة في `enqueue` و`claimNextJob`
و`completeJob` و`failJob` و`cancelJob`. الإدراج من خمس رحلات إلى ثلاث،
والمطالبة من ثلاث إلى اثنتين.

**بعد طرح المسافة:** ٢.٢ رحلة لكل مطالبة. عامل داخل نفس منطقة القاعدة
(زمن رحلة ~٥ م.ث) يعطي **~١١ مللي ثانية** — أي **تحت حد المراجعة
المعماري (١٠٠ م.ث) بتسعة أضعاف**.

**ملاحظة على المؤشّر نفسه:** سكربت القياس كان يقارن الرقم الخام بالحد،
فيعطي إنذارًا كاذبًا دائمًا عند التشغيل من جهاز بعيد. صار يقيس زمن
الرحلة المرجعي أولًا ويقارن بعدد الرحلات — الحد مقصود به عاملًا داخل
المنطقة، لا قياسًا عبر القارات.

**قيمة جانبية:** كل رحلة شبكة محذوفة هي نقل صادر محذوف — والمشروع
متجاوز حصته تسعة أضعاف.

## ١٤. الأمان

| الطبقة | ما تفرضه |
|---|---|
| `canEnqueue` | الدور (هرمي) + حالة الحساب + العضوية في المشروع |
| `canControlJob` | صاحب المهمة أو مسؤول فقط |
| `canViewQueueDashboard` | مسؤول فقط |
| RLS | قراءة للمسجّلين، وكل الكتابات عبر عميل الخدمة |
| دوال القاعدة | `revoke` من العامة، و`grant` لدور الخدمة فقط |

**قرار مقصود:** المسؤول يعبر فحص العضوية. بدون ذلك تتعذّر إدارة مشاريع
لم ينضمّ إليها، وهذه عرقلة تشغيلية لا عزل أمني.

**قرار مقصود آخر:** التحكّم في المهمة أضيق من إدراجها. زميل في نفس
المشروع **لا** يلغي مهمة غيره — الإلغاء يرمي عملًا قد يكون مدفوع الثمن.

---

## ١٥. الأحداث

```
queue.job.created · started · progress · completed · failed
queue.job.canceled · retrying · dead_lettered
queue.worker.started · stopped · failed
queue.state.empty · overloaded
```

تُنشر في `platform_events` القائم (ترحيل ٠٠٦٣) بمفتاح منع تكرار، فسقوط
العامل في منتصف الكتابة لا ينشر الحدث مرتين.

**فشل النشر لا يُسقط المهمة.** حدث لم يُنشر مزعج؛ ومهمة نجحت ثم سقطت
بسبب فشل النشر أسوأ بكثير.

---

## ١٦. المراقبة

`/api/health/queue` يعيد عمق الطابور، ونسبة الفشل، والأعداد بالحالة،
وأقدم مهمة منتظرة، ومتوسطي التنفيذ والانتظار، والرسائل الميتة، وحالة كل
عامل — و**٥٠٣ عند الحالة الحرجة** لترصده أنظمة المراقبة الخارجية.

**الحالة الوحيدة التي تُصنَّف حرجة فورًا:** طابور فيه شغل بلا أي عامل
حيّ. كل مقياس منفرد يبدو مقبولًا هنا، والنظم الساذجة تعرضها تحذيرًا
أصفر — والحقيقة أن لا شيء سيُنفَّذ أبدًا.

3. قياس أداء المطالبة على قاعدة حقيقية — الأرقام هنا للمنطق لا للقاعدة.
4. **تفعيل النسخ الاحتياطي** — شرط مسبق مذكور في وثيقة التصميم.
